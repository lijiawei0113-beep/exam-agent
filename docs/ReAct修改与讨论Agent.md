# ReAct 修改与讨论 Agent

本文说明三件事：ReAct 是什么，这个项目为什么在"修改与讨论"环节使用它，以及它具体做了什么、怎么评测。

代码位置：

- `src/exam_agent/agents/edit_agent.py`：ReAct 循环、工具、停止条件、上下文压缩
- `src/exam_agent/editing.py`：修改方案的校验与执行，包括 `restore` 和 `patch` 两个操作
- `src/exam_agent/experiments/edit_eval.py`：对比实验

---

## 1. ReAct 是什么

ReAct 是 Reasoning + Acting 的缩写，出自 Yao 等人 2022 年的论文 *ReAct: Synergizing Reasoning and Acting in Language Models*。核心思想是：模型不必一次答完，而是在"思考"和"行动"之间交替进行。

```
思考：老师说的"讲苹果的那题"是哪道？我需要搜一下
行动：search_questions("苹果")
观察：第 9 题（应用题）原文包含"苹果有 96 个、梨有 58 个"
思考：找到了，再读全文确认难度
行动：get_question(9)
观察：……完整题干、答案、解析……
思考：可以给出修改方案了
行动：submit_plan(rewrite 第 9 题，降低难度)
```

它和"一次调用直接出答案"的区别：

| | 一次调用 | ReAct |
|---|---|---|
| 信息来源 | 事先塞进提示词的内容 | 模型按需调用工具获取 |
| 适合的问题 | 需要什么信息事先确定 | 需要什么信息要看具体问题 |
| 优点 | 快、便宜、可预测 | 能处理开放问题，回答有依据 |
| 缺点 | 信息给少了答不了，给多了浪费 token | 调用次数多，可能原地打转，需要停止条件 |

工业界一般用模型的原生函数调用（function calling）来实现 ReAct。本项目也是这样做的：DeepSeek 的 OpenAI 兼容接口 + `tools` 参数。没有使用 LangChain 等框架。

## 2. 为什么这个项目在这里用 ReAct

### 2.1 旧做法的问题

修改规划员原来只调用一次模型，每道题它只能看到一行摘要：题型、分值、难度、知识点、题干前 50 字、答案前 15 字。下面这些老师的说法，它处理不好：

| 老师的话 | 一次调用为什么不行 |
|---|---|
| "把讲苹果和梨的那道题改简单些" | "苹果"在题干第 50 字之后，摘要里看不到 |
| "讲机器人的那篇阅读太难了" | 英语阅读题干开头是作答说明，前 50 字看不到短文 |
| "第 1 题为什么选 A？" | 看不到选项和解析，回答容易编造 |
| "选择题答案是不是太集中了？" | 摘要里没有统计数据 |
| "把第 3 题改回原来的" | 看不到版本历史；整卷撤销会连带丢掉其他题后来的修改 |
| "第 8 题是不是超纲了？" | 看不到课程知识库 |
| "第 12 题短文多少词，符合要求吗？" | 模型数不准词数，需要程序统计 |

如果把整卷全文、全部历史版本、知识库都塞进提示词，一份 20 题的卷子加上几个版本，上下文会很长，而且大部分信息与当前这句话无关。

### 2.2 为什么只在这里用

| 环节 | 用不用 ReAct | 原因 |
|---|---|---|
| 出卷（理解需求 → 规划 → 命题 → 审核） | 不用，由代码编排 | 每一步做什么是确定的，固定流程更可靠、更便宜 |
| 验证答案（用哪个工具核对） | 不用，由代码路由 | 可靠性优先，路由规则可以写死并测试 |
| 修改与讨论 | 用 | 老师的说法千变万化，要查什么事先无法确定 |

面试时要讲清楚的一点：**不是所有环节都适合让模型自主决策。** 只在"信息需求无法事先确定"的地方用 ReAct，其他地方用确定性编排。

## 3. 它做了什么

### 3.1 工具（全部只读）

| 工具 | 作用 | 对应的老师说法 |
|---|---|---|
| `get_question(position)` | 读一道题的全文：题干、选项、答案、解析、知识点、验证状态 | "第 1 题为什么选 A" |
| `search_questions(query)` | 全卷全文搜索，原文包含的排在前面，其余按 BM25 打分 | "讲苹果的那题""答案是 288 的题" |
| `paper_stats()` | 全卷统计：题型分值、难度分布、选择题答案分布、知识点重复、验证状态、英语短文词数 | "答案是不是太集中""哪些题要我确认" |
| `get_history(position?)` | 版本历史；给了题号时，只列出这道题内容发生变化的版本 | "改回原来的""我改过几次" |
| `get_question_version(position, version)` | 读某道题在某个旧版本中的全文 | "上一版那道是什么样的" |
| `lookup_scope(query?, position?)` | 查课程知识库，判断是本单元、已学过还是超纲（Agentic RAG） | "第 8 题超纲了吗" |
| `check_question(position)` | 用程序工具核对：精确计算、解方程、英语语法级别与字数，不经过模型 | "第 10 题答案对吗" |
| `submit_plan(action, ops, reply)` | 结束本轮，提交回答、追问或修改方案 | — |

### 3.2 读写分离：模型只能读，不能写

```
老师的话 → ReAct（只读工具查阅） → submit_plan 提交方案
                                          ↓
                         apply_ops 用代码校验（题号、分值守恒、版本存在、改字唯一定位）
                           ↓ 不通过                     ↓ 通过
               原因作为工具结果退回给模型修正      命题 / 恢复 / 改字 → 审核 → 存新版本
```

模型从不直接写数据库。题数和总分守恒、只改目标题（内容指纹校验）、版本号与乐观并发，都由代码保证。

### 3.3 支持的动作和操作

动作有四种：

- `answer`：回答或讨论。谈具体题目前必须先读全文。可以提出建议，但不擅自改卷。
- `clarify`：指代不明时追问。
- `edit`：执行修改。
- `export`：导出 PDF。

修改操作，其中 `restore` 和 `patch` 是本次新增的：

| 操作 | 说明 |
|---|---|
| `rewrite` | 重出一道题（可以改难度、知识点） |
| `retype` / `add` / `remove` | 改题型 / 加题 / 删题，分值由代码重新分配 |
| `rescore` / `set_total` | 老师明确指定分值或满分 |
| `add_constraint` | 持续有效的要求（如"答案都要是整数"），并回溯核验现有题目 |
| **`restore`** | 只把一道题恢复成某个旧版本。和整卷撤销不同，不会丢掉其他题后来的修改 |
| **`patch`** | 局部改字。原文必须恰好出现一次，避免改错地方；改完重新核验，答案不对会进入返修 |

**"先建议、再执行"的多轮讨论示例：**

```
老师：第 4 题有什么问题吗？
助手：（读全文后）选项 A 和 B 都能成立，存在两个正确答案。建议把选项 B 改成 "Monday"。要我这样改吗？
老师：好，就按你说的改
助手：（看到上一轮的建议）提交 patch：第 4 题选项 "maths and science" → "Monday"
```

### 3.4 停止条件

| 情况 | 处理 |
|---|---|
| 查阅超过 8 轮，或只读工具累计调用 10 次 | 只允许调用 `submit_plan`，强制提交；信息不足就追问老师。（一轮可以并行调用多个工具，只限轮数不够：实验 1 中统计类问题曾查到 24 次） |
| 模型没有调用工具，直接用文字回复 | 再强制它用 `submit_plan` 归类为回答、追问或修改（实验 1 中追问曾被当成回答） |
| 同一工具、同样参数重复调用 | 返回"刚才已经查过"；重复两次视为原地打转，强制提交 |
| 方案连续 3 次被代码退回 | 停止，改为向老师说明原因并追问 |
| 题号明确的简单指令 | 提示词要求不调工具，直接提交，避免浪费 |

### 3.5 上下文控制（按需加载 + 压缩）

- 一开始只给模型每题一行的**索引**，全文按需读取。
- 最近 3 条工具结果保留全文，更早的压缩成一行摘要，例如：`（较早的工具结果已压缩）get_question({"position": 1}) → 第1题 | 选择题 | 5分 …`。
- 单条工具结果最多 1500 字。
- 对话历史只带最近 4 轮。试卷的准确状态、持续约束、版本历史都从数据库读取，不依赖聊天原文。

### 3.6 可观测

每一步的工具名、参数和结果摘要都写进运行轨迹（`trace_events` 表）。

- 网页进度会实时显示"查看第 9 题全文""在试卷中搜索'苹果'""方案被程序退回：……"。
- 命令行对话里，每一步显示为一行灰字。

## 4. 怎么评测

### 4.1 评测设计

**对比对象：**

- `oneshot`：原来的一次调用（只看摘要），作为基线；
- `react`：本文的 ReAct Agent。

**评测范围**：只评测"规划"这一步，也就是理解老师的话、给出方案或回答。不调用命题员，所以便宜、可重复。

**数据：**

- `evals/edit_eval/papers.json`：两份试卷。
  - 三年级上册数学，共 3 个版本：v2 改过第 3 题，v3 改过第 6 题。
  - 五年级上册英语。两篇阅读短文分别为 97 词和 86 词，都低于五年级 100 词的下限。第 4 题故意设成有两个正确选项。
- `evals/edit_cases.jsonl`：31 条老师的话，分 10 类：

| 类别 | 例子 | 期望 |
|---|---|---|
| 题号明确 | "第 7 题太难，换一道简单点的" | edit / rewrite / 第 7 题 |
| 按内容指代 | "把讲苹果和梨的那道题改简单些" | edit / rewrite / 第 9 题 |
| 局部改字 | "第 6 题的 278 改成 268" | edit / patch / 第 6 题 |
| 历史版本 | "把第 3 题改回原来的" | edit / restore / 第 3 题 / v1 |
| 题目细节问答 | "第 1 题为什么选 A？" | answer，回答中含 "603" |
| 全卷统计 | "第 12 题的短文有多少词？符合要求吗？" | answer，含 "86" 和"不符合 / 不足" |
| 是否超纲 | "第 8 题是不是超纲了？" | answer，含"没有超纲 / 范围内" |
| 开放讨论 | "这份卷整体难度怎么样？" | answer |
| 应当追问 | "把那道题改一下" | clarify |
| 同意上一轮建议 | （上一轮建议改第 4 题）"好，就按你说的改" | edit / patch 或 rewrite / 第 4 题 |

**判分规则：**

- 动作必须正确；
- 修改类：操作类型和题号正确，恢复类还要求版本正确；
- 问答类：每组关键词至少命中一个。

**指标：** 总体正确率、各类正确率、平均工具调用次数、模型调用次数、token、耗时。

### 4.2 运行步骤（Windows + PyCharm）

1. 把 v9.0 补丁覆盖到 `D:\exam-agent`，先确认测试全部通过：

   ```powershell
   cd D:\exam-agent
   pytest
   ```

2. 先试跑几条，确认 API 和工具调用正常：

   ```powershell
   python -m exam_agent eval-edit --cases m03,m09,m13,e06
   ```

   每条会实时显示 ✓ 或 ✗ 和工具调用次数。如果报错与 `tools` 参数有关，把报错发给我（截图记得给 API Key 打码）。

3. 正式跑全部 31 条，两种方式各重复 3 次（约 190 次规划，大部分是 ReAct 的多轮调用）：

   ```powershell
   python -m exam_agent eval-edit --repeats 3
   ```

   只跑一种方式时，用 `--planners react` 或 `--planners oneshot`。

4. 结果在 `evals\results\` 下：
   - `edit_eval_<时间>.md`：总体表、分类表、每条错误的原因和模型回复；
   - `edit_eval_<时间>.json`：全部原始数据，包括每条的操作、回复、工具次数、token。

5. 把 `.md` 发给我，我帮你做误差分析：哪些错误是模型理解问题、哪些是判分规则太严、哪些是工具设计问题。改进后再跑一次，记为实验 2。

### 4.3 预期与怎么解读

- **预期提升最大的类别**：按内容指代、历史版本、细节问答、全卷统计、是否超纲。这些正是一次调用"看不到信息"的地方。
- **预期持平的类别**：题号明确、应当追问。ReAct 在题号明确时理想情况下是零工具调用、直接提交。如果它在这类指令上也频繁调用工具，说明提示词需要调整。
- **成本**：ReAct 每条多 1～3 次模型调用，token 和耗时会上升。报告时要同时给出"正确率提升"和"成本增加"，这就是你最初要求的"用实验解释收益和成本"。
- **基线必然失败的类别**：一次调用的提示词里没有 `restore` 和 `patch` 操作，所以这两类正确率接近 0。解读时要说明这一点，不能把它算作 ReAct 本身的功劳。更公平的说法是"新能力 + 按需查阅"带来的提升。

### 4.4 局限（面试时主动说明）

- 数据集为作者自建：开发集 35 条，留出集 18 条，共三份试卷；开发集中 1 条约占 3 个百分点。
- 开发集被用来调提示词，报告时以留出集为准。
- 问答类按关键词判分，只能证明"回答依据了正确的事实"，不能衡量表达质量。
- 只测一个模型。模型的随机性用重复 3 次来缓解。

### 4.5 实验 1 结果（2026-10-25，deepseek-flash，31 条 × 3 次）

| 方式 | 正确率 | 工具调用/条 | token/条 | 耗时秒/条 |
|---|---|---|---|---|
| 一次调用 | 65% | 0 | 1307 | 1.4 |
| ReAct | 77%（修正判分后 81%） | 3.6 | 8362 | 5.6 |

| 类别 | 一次调用 | ReAct |
|---|---|---|
| 题目细节问答 | 40% | 100% |
| 全卷统计 | 50% | 92% |
| 局部改字 / 历史版本 | 0% / 0%（基线没有这些操作和数据） | 89% / 56% |
| 按内容指代 | 100% | 50% |
| 应当追问 / 同意上一轮建议 | 100% / 100% | 50% / 33% |

**ReAct 的 21 次错误归因：**

| 原因 | 次数 | 处理 |
|---|---|---|
| 老师要求修改，却只分析或反问（"换一下有两种理解……"） | 10 | 提示词：祈使句直接执行，没说怎么改就用 rewrite |
| 用文字向老师追问，被当成回答 | 3 | 代码：文字回复再用 submit_plan 归类 |
| 改选项时带了"D. "前缀，原文匹配失败 | 3 | 代码：自动去掉字母前缀（工具设计缺陷） |
| 判分错误：恢复到 v1，与期望的 v2 内容相同 | 3 | 修正判分规则：比较内容，不比较版本号 |
| "改简单些"用了局部改字，而不是换题 | 1 | 提示词：只有老师给出具体原文和新文字时才用 patch |
| 把"已验证"误读为"需要确认"（同时逐题查阅了 13 次） | 1 | 统计工具直接给出"需要老师确认的题"；工具总调用上限 10 次 |

**几点发现：**

- 去掉基线不具备的"局部改字"和"历史版本"两类后，两者正确率几乎相同（基线 80%，ReAct 79%）。也就是说，ReAct 在问答和统计上的收益，被"该动手时不动手"的损失抵消了。这是一个提示词设计问题："先建议、再执行"的规则被模型过度泛化到了明确的修改指令上。
- 基线只看摘要时会**编造缺陷**：两次说第 9 题"题干被截断"，其实只是摘要截断了题干。这正是"只给摘要"的风险。
- 按内容指代这一类，基线是 100%，因为原用例的关键词恰好在题干前 50 字内，区分不出两种方式。已补 4 条关键词只出现在短文中间或解析里的用例（m22、m23、e11、e12）。
- 成本：ReAct 的 token 约为 6.4 倍，耗时约为 4 倍。

修正后重跑，记为实验 2。

### 4.6 实验 2 结果（2026-10-25，开发集 35 条 × 3 次）

| 方式 | 正确率 | 工具调用/条 | 模型调用/条 | token/条 | 耗时秒/条 |
|---|---|---|---|---|---|
| 一次调用 | 70% | 0 | 1.0 | 1315 | 1.5 |
| ReAct | **95%** | 2.0（实验 1：3.6） | 2.9 | 7695 | 5.2 |

- 去掉基线不具备的"局部改字"和"历史版本"两类后：基线 84%，ReAct 95%。实验 1 时两者打平，这次 ReAct 领先 11 个百分点。
- 历史版本、同意上一轮建议、题号明确，都升到了 100%；工具调用从 3.6 次降到 2.0 次。
- 剩余 5 次错误：
  - 2 次：回答了问题后又顺带问一句，被标成"追问"；
  - 1 次：该追问时猜了一道题去改（e09 "这个不太好，改一下"）。这是实际使用中代价最大的一类错误；
  - 2 次：过于谨慎（m05、m07）。
  - v9.2 针对前两类调整了提示词。
- 新补的 4 条"按内容指代"用例，基线也全对：摘要里的知识点名称（如"机器人阅读"）已经泄露了内容。这一类在当前数据上仍然区分不出两种方式，要如实说明。
- **为什么要留出集**：实验 1 → 2 是看着开发集的错误改的提示词，95% 偏乐观。因此另建 18 条留出集用例（`split: holdout`），包括一份新试卷（四年级上册数学）和新的说法。留出集只在最后评测一次，不据此调参。运行：`python -m exam_agent eval-edit --split holdout --repeats 3`。

- 基线的错误都是"看不到信息"造成的，而且它会**自信地给出错误回答**，并不承认自己看不到：

  - "第 5 题之前是什么题？"三次都理解成"第 4 题是什么"，因为它看不到版本历史；
  - 一次还说"没有修改选项的操作，请您在编辑器里改"。
- ReAct 在留出集上全部正确。每条平均查 1.6 次工具，比开发集少，说明在题号明确的指令上它没有多余调用。
- 成本：token 约为基线的 5.6 倍，耗时约为 3.3 倍。

**如何看待 100%：**

- 只有 18 条不同的用例。三次重复不是独立样本，按 18 条计算，正确率 95% 置信区间的下限约为 82%（Wilson 区间）。只能说"在这些情形上稳定正确"，不能说"总是正确"。
- 留出集和提示词都出自同一作者，说法风格可能相近。最好的补充是收集真实老师的修改说法。
- "按内容指代"和"细节问答"两类，基线在留出集上也是 100%，ReAct 的优势主要体现在统计、历史版本和局部改字三类。

## 5. 简历可用表述

> 设计试卷修改与讨论 ReAct Agent：7 个只读工具（全文读取、全卷检索、统计、版本历史、课程知识库、程序核对）+ "代码校验后执行"的读写分离，配合步数与调用上限、重复检测、上下文压缩；新增单题恢复和局部改字。在 18 条留出集指令上，规划正确率由一次调用式的 67% 提升至 100%（剔除基线不具备的能力后为 92% → 100%），代价为约 5.6 倍 token、3.3 倍耗时。通过开发集逐条错误归因迭代提示词和工具（ReAct 错误从 21 次降到 5 次），并用未参与调参的留出集报告最终结果。
